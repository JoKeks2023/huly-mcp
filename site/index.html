01 — Quick setup

Pick your client. Paste. Done.

Account credentials only. The server finds your workspaces itself — no workspace to configure.

terminal 
claude mcp add huly \
  -e HULY_EMAIL=you@example.com \
  -e HULY_PASSWORD=your-password \
  -- npx -y huly-mcp-selfhost

Add --scope user (all projects) or --scope project (.mcp.json — don’t commit secrets) after “add huly”. Check with: claude mcp list

SSO account without a password? Use HULY_TOKEN instead — see Authentication. More clients (Windsurf, Cline, Continue) in the README.

03 — Multi-workspace

One login. Every workspace.

The server discovers what your account can access and keeps a separate connection per workspace. It never guesses which one you mean.

  • One account login — email + password or token, once per process.
  • Discovery via getUserWorkspaces(); list_workspaces shows name, slug and id.
  • One cached connection per workspace, opened on first use via selectWorkspace() with its own workspace token.
  • No current, default or last-used workspace. Every call names its target.
  • Writes require workspace — enforced by the tool schema, even with a single workspace.
  • Reads may omit it only when exactly one workspace is available. IDs like PROJ-1 are only unique within their workspace.

05 — Architecture

A thin, stateful bridge.

No database, no cache service, no extra infrastructure. All state is in process memory: one account session, the discovered workspace list and one connection per workspace in use.

MCP clientClaude · Codex · Cursor · Zed

Calls tools over stdio — or HTTP when running the Docker image behind mcp-proxy.

MCP toolssrc/tools/*.ts

48 handlers. Each resolves its own connection from its workspace argument; inputs are validated against zod schemas first.

Account clientHULY_ACCOUNTS_URL · account token

login / getLoginInfoByToken, then getUserWorkspaces() and selectWorkspace(). Never holds a workspace token.

Workspace connection managersrc/connection.ts

Caches the session, the workspace list and one connection per workspace id. Failed attempts are not cached; shutdown closes everything.

Workspace clientper workspace · workspace token

TxOperations for all reads and writes, plus a workspace-scoped account client for getWorkspaceMembers().

Huly WebSocketendpoint from selectWorkspace()

Opened with @hcengineering/server-client; loads the workspace model once, then stays open.

Storage / /filesHULY_FRONT_URL · workspace token

Markup blobs (document bodies, descriptions) and attachments — Bearer-authenticated, per workspace.

06 — Self-hosted

Built for huly-selfhost. Works on Huly Cloud.

Upstream writes document content through Huly Cloud’s datalake service, which self-hosted instances don’t run. This fork routes blobs through the front service’s own /files endpoint instead.

HULY_ACCOUNTS_URL

Account service: login, workspace discovery, selectWorkspace(), members. Defaults to https://account.huly.app. Self-hosted: e.g. https://your-huly-instance.com/_accounts.

HULY_FRONT_URL

Front service: reads document and description content and — when set — handles uploads via /files. Not involved in login or discovery. Self-hosted: e.g. https://your-huly-instance.com.

07 — Security

Tokens stay in headers.

Content fetches in get_document, get_issue and get_organization used to put the workspace token into the /files URL — and get_document printed that URL into the tool result. Now the token only travels as an Authorization header.

  • No /files URL carries token=.
  • No tool result contains a workspace token — covered by regression tests.
  • Each request uses the token of the workspace named in the call.
Security in the docs →
GET /files — before → after
- GET /files?file=<blob>&workspace=<uuid>&token=<workspace token>
+ GET /files?file=<blob>&workspace=<uuid>
+ Authorization: Bearer <workspace token>

Remote deployments: the Docker image does not authenticate MCP clients. Anyone who can reach it acts as your Huly account — put it behind an authenticating reverse proxy or a private network.

08 — Install

Three ways to run it.

npm

Launched by your MCP client over stdio. Node.js ≥ 20.

terminal
npx -y huly-mcp-selfhost

From source

Point your client at node /path/to/huly-mcp/dist/index.js.

terminal
git clone https://github.com/JoKeks2023/huly-mcp.git
cd huly-mcp && npm install && npm run build

Docker

HTTP via mcp-proxy on port 8000: /mcp (streamable HTTP) and /sse. Credentials in .env.

terminal
docker run -d --name huly-mcp -p 127.0.0.1:8000:8000 \
  --env-file .env jokeks2023/huly-mcp:latest

Remote clients connect to https://<your-host>/mcp through your own authenticating proxy.
